Five semaphore patterns, one step at a time

Each program below runs on a simulated single CPU. You can watch the threads take turns on the processor, follow each thread's program counter through its code, and see them block on and wake from semaphore locks. Press Run to let the scheduler decide, or press a thread's "Run next line" button to schedule it yourself. Every demo also has a broken version so you can see what the semaphore is preventing.

sem_waitIf the value is above 0, decrement it and continue. If it is 0, block until someone posts.
sem_postIf a thread is blocked, wake one up. Otherwise increment the value.

00 · How to read the demos

A semaphore is a counter with a waiting line

Every demo is laid out the same way. The CPU runs one thread at a time and shows the line it just executed. Each thread has a card with its own code: ▶ marks its next line (its program counter), ■ means it is blocked, and z means it is sleeping. Each semaphore is drawn as a padlock that is green and open while its value is above 0, red and shut at 0, with the threads blocked on it listed underneath. Threads that are not on the CPU wait in the ready queue, in a lock's queue, or asleep.

The two operations

sem_wait(s):            /* a.k.a. P, down, acquire */
  if (s.value > 0) s.value--;
  else block this thread on s.queue;

sem_post(s):            /* a.k.a. V, up, release */
  if (s.queue not empty) wake one thread;
  else s.value++;

Each step runs atomically, so no two threads can both see value 1 and both decrement it. The simulator hands the woken thread straight through its sem_wait. POSIX instead increments the value and lets the woken thread decrement it, which ends up in the same state.

01 · serialization.c · signaling

B must not pour until A has boiled the water

B is created first and A sleeps before boiling, so without coordination B would run first. done starts at 0, which means "not yet". B blocks on it until A's sem_post says the water is ready.

Pattern: initialize to 0. The thread that must go second calls sem_wait and the thread that goes first calls sem_post when it is finished. The order holds even if B starts waiting long before A finishes.

02 · rendezvous.c · two-way signaling

  
Neither Alice nor Bob may leave until both have arrived

  
This is serialization in both directions at once. Each thread announces its own arrival with sem_post, then waits for the other's announcement. Bob is late (sleep(1)), so Alice ends up waiting on bob_here.

  

  
Order matters: signal first, then wait. If both threads wait before they signal (try "Wait, then signal"), each one is blocked waiting for a post the other will never reach. That is a deadlock.

  
Original source: rendezvous.c










  
03 · pingpong.c · strict alternation

  
Two semaphores pass a single turn back and forth

  
Exactly one of ping_turn and pong_turn holds a 1 at any time, and that 1 is the turn. Each thread spends the turn (sem_wait on its own semaphore), prints, then hands the turn to the other (sem_post on the other semaphore). Change the initial values to see how alternation breaks.

  

  
The initial values are the whole design. (1, 0) means ping goes first. (0, 0) means nobody has the turn, so both threads deadlock. (1, 1) means both have a turn and can print out of order.

  
Original source: pingpong.c










  
04 · tickets.c · mutual exclusion

  
Two sellers, one shared counter

  
tickets-- and sold++ are not atomic. Each one loads the value into a register, changes it there, and stores it back, and the simulator shows those as separate steps. The mutex semaphore (initial value 1) lets only one seller between sem_wait and sem_post at a time. The real program sells 100,000 tickets; here you can step through 5, 10 or 20, or run the full 100,000 at the bottom.

  

  
Two ways to break it: remove the mutex and the sellers' load and store steps interleave, so updates are lost and tickets can be oversold. Keep the mutex but return without sem_post on the sold-out path, and the first seller to finish leaves the counter locked forever. That is why the source says "release first!"

  
Original source: tickets.c










  
05 · parking.c · counting semaphore

  
Six cars, three spots

  
A counting semaphore starts at N, the number of identical resources. Each sem_wait takes one and each sem_post returns one. When the count reaches 0, the next car queues at the gate until someone leaves. Change the number of spots and cars, or remove the semaphore and watch the lot overflow.

  

  
Pattern (multiplex): initialize to N to allow at most N threads in a region at once. A mutex is the special case N = 1. The semaphore only counts free spots. It doesn't say which spot a car gets, so the drawing picks the first free one.

  
Original source: parking.c
